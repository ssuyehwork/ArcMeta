应用分为"SQLite 内存模式"和"磁盘目录模式"两种。两者运行时各自独立，相互不干扰、井水不犯河水，不共享判断逻辑、不共享数据加载路径。

# 1. 关于“我的分类”与“快速访问”的关联

## 1.1 概念与绑定机制
在侧边栏分类树中，“我的分类”（User Category）与“快速访问”（Quick Access / Favorite Group）本质上共享同一套底层的物理分类表 `categories`。
其中，“我的分类”是基于 parentId 继承链构建的树状分层结构。而“快速访问”则是一组扁平、置顶的镜像代理节点容器。

## 1.2 置顶关联数据模型
每个物理分类在底层数据表 `categories` 中都有一个布尔值属性 `pinned`，代表该分类的置顶状态。
在模型构建（CategoryModel）中：
- 渲染正常自定义分类树时：遍历全部类别并挂载。物理分类节点的 `PinnedRole` 绑定其对应的 `pinned` 属性。
- 渲染“快速访问”分组节点时：系统会遍历所有类别。只要分类的 `pinned` 属性为 `true`（或 1），系统就会在此分组节点下创建一个全新的 **镜像代理节点（Mirror Item）**。
- 该镜像代理节点底层绑定相同的物理 `IdRole`（同为 `cat.id`）、`TypeRole` 等属性，实现高强度的关联和逻辑复用。

## 1.3 交互联动生命周期
在 UI 层（CategoryPanel），右键单击某个具体分类时：
- 若未置顶，右键菜单显示 “添加至‘快速访问’”。点击后将对应分类的 `cat.pinned` 改为 `true`，通过 `CategoryRepo::update(cat)` 持久化落盘并刷新模型。
- 若已置顶，右键菜单显示 “从‘快速访问’中移除”。点击后将对应分类的 `cat.pinned` 改为 `false`，通过 `CategoryRepo::update(cat)` 持久化落盘并刷新模型。
- 不管是从正常自定义树还是置顶列表中点击同一 ID 的节点，两边最终都分发相同的 ID 给逻辑处理模块，保证无缝穿透、完全联动。

# 2. 关于“分类文件加载与架构收拢”

## 2.1 物理路径前缀枚举分类文件逻辑的彻底废除
侧边栏分类模式加载分类内容时，100% 仅允许通过中心化的 SQLite 数据库关联表（`category_items`）直接读取映射数据。
严禁在任何地方使用物理路径前缀匹配 + 内存扫描（如针对 `parentId == 0` 且 physicalPath 非空的根分类，通过 `MetadataManager::forEachCachedItem` 进行模糊前缀匹配）来枚举和统计分类内的文件。所有的统计、条数对账以及列表展示，统一收拢至数据库读取逻辑。

## 2.2 辅助元数据过滤规范
磁盘上物理存在的 `.scch` / `metadata.scch` 后缀名文件是系统的辅助元数据缓存。在分类和文件列表检索时，必须统一且始终将其过滤掉，防止辅助文件被作为常规资产加载。修改注释或清理代码时，不得改动过滤逻辑本身，仅可将其中的描述性英文（如 SCCH 架构）修正为中性含义描述。

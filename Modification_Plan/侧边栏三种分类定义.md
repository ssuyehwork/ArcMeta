您梳理的这个**三层分类模型（静态、半静态、全动态）**非常精准且直击底层本质！

基于您的三层定义，系统的底层职责和交互边界必须严格这样划分，彻底消灭以往的逻辑混淆：

---

### 1. 静态分类（系统固定桶）
- **涵盖**：`全部数据`、`未分类`、`未标签`、`最近访问`、`标签管理`、`回收站`。
- **物理与生命周期特征**：
  - **永恒存在**，不可删除、不可重命名、不可拖拽改变层级。
  - **数据机制**：全内存/全分库的“聚合计算视图”，不属于任何单个硬盘，根据当前所有已挂载的硬盘实时汇聚。

---

### 2. 半静态分类（物理托管库）
- **涵盖**：所有 `ArcMeta.Library_%`（如 G 盘托管库、H 盘托管库）。
- **物理与生命周期特征**：
  - **由硬件生命周期驱动**：插入硬盘时自动挂载并显示，拔出硬盘时自动从侧边栏卸载；
  - **不可由用户随意删除或重命名**（因为它是物理硬盘的根节点容器）；
  - **计数特征**：其计数 **严格 = 该硬盘内托管的素材总数**（杜绝显示为 0 的 Bug）；
  - **UI 展示**：在侧边栏显示为优雅的驱动器/盘符形态（如 `本地磁盘 (G:)`），严禁将底层代码名 `ArcMeta.Library_G` 裸露给用户。

---

### 3. 全动态分类（用户组织树）
- **涵盖**：“快速访问”（收藏镜像）与“文件夹”下的所有层级分类（包括用户手动创建、自动导入生成的分类文件夹）。
- **物理与生命周期特征**：
  - **用户主权**：允许自由创建、删除、重命名、嵌套、设色、拖拽排序、设置密码；
  - **数据机制**：通过 `category_items` 与具体的素材 FID 建立关联，属于纯粹的内容组织层。

---

这个三层定义把**“系统聚合层 -> 物理硬件层 -> 用户业务层”**的界限划得一清二楚。
如果您认可这套梳理，我们后续所有的代码重构（数据写入、动态计数、UI 树组装、热拔插监听）将全面以这个三层标准为唯一基准推进。

### 一、 为什么之前会出现差异（显示为 0、数字对不上）？

之前的代码犯了典型的**职责分散**与**逻辑撕裂**错误：
1. **系统分类**在 `getSystemCounts()` 里用一套 SQL 查；
2. **普通分类**在 `getCounts()` 里用另一套 JOIN SQL 查；
3. **半静态托管库（`ArcMeta.Library_%`）** 没人管它，直接被当成普通分类去查 `category_items`，查不到关联就直接变成了 `(0)`；
4. **侧边栏 UI 树** 在 `CategoryModel` 和 `CategoryPanel` 里又各自有一些补丁判断。

各算各的、多头管理，导致“全部数据”是 19，而下面的托管库全是 0，前后自相矛盾。

---

### 二、 统一权威计数的唯一计算函数方案

必须设计一个单一职责的计算函数（如 `CategoryRepo::calculateAllStatistics()`），一次性完成**静态、半静态、全动态**的权威计算，并输出一张不可篡改的统计账本：

```
[权威计数函数 calculateAllStatistics()]
   │
   ├── 1. 静态分类统计 (全库聚合)
   │     ├── 全部数据 = 各盘有效资产相加之和 (19)
   │     ├── 未分类   = 存在于库中但未加入任何【全动态用户分类】的素材数
   │     ├── 未标签   = 标签列表为空的素材数
   │     ├── 回收站   = 各盘已标记删除 (is_trash=1) + 物理回收站记录
   │     └── 最近访问 / 标签管理...
   │
   ├── 2. 半静态分类统计 (按物理盘隔离计算)
   │     └── 遍历已挂载盘符：每个托管库计数 = 对应盘数据库中 (is_trash=0) 的总资产数 (G盘: 19, H盘: 0)
   │
   └── 3. 全动态分类统计 (按分类关联计算)
         └── 遍历用户分类：该分类 ID 在 category_items 中关联的去重有效资产数
```

### 三、 改造后的效果
1. **绝对一致**：UI 只需要把这一张账本拿到，各节点根据自己的 ID/类型直接取值显示，**杜绝任何两处计算逻辑不一致的可能**；
2. **逻辑纯粹**：不管是冷启动、热拔插硬盘、导入素材还是删除分类，全系统只触发这同一个函数重新出账，彻底根除维护噩梦。

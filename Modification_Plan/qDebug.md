# 正式版调试日志清理 —— 分析委托

## 任务范围
全项目排查所有 qDebug / qInfo / std::cout / printf 等纯调试性质的日志输出，
以及任何被误用为 qDebug 但实际内容是失败/异常/降级情况的日志调用。

## 处理原则（三分类，不允许一刀切）

1. 纯调试跟踪信息（进度提示、变量值打印、"进入XX函数""正在执行XX步骤"
   这类对用户/运维无排障价值的输出）——物理删除代码行，不允许注释掉、
   不允许用宏开关包裹（如 #ifdef DEBUG）保留，不允许保留空的日志调用框架
   留待"以后可能用得上"。

2. 内容属于失败/异常/降级但被错误标记为 qDebug 的日志（例如数据库打开
   失败、Schema错误、文件操作失败类信息）——不删除，改为 qWarning 或
   qCritical（根据严重程度判断：可恢复的降级用 qWarning，导致功能不可用
   的用 qCritical），保留在正式版中，作为生产环境排障依据。

3. 已经是 qWarning / qCritical 的错误告警——原样保留，不做任何改动。

## 强制要求
- 每一处改动必须能说明属于上述三类中的哪一类，不允许模糊处理
- 判断某处日志属于第1类还是第2类时，如果内容本身不含"失败""错误""异常"
  等明确失败语义、且无法确定是否有排障价值，禁止自行判断删除，必须列入
  待确认清单交由用户裁定，不得自行假设"看起来不重要就删掉"
- 清理完成后，全项目重新执行一次 grep 检索确认，物理删除的部分不允许有
  任何残留（包括被注释掉但未删除的代码行）

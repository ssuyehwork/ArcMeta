# ArcMeta 核心架构与规划总账 —— Architecture and Planning.md

> 本文档是 ArcMeta 全项目唯一的、合一的顶层架构、功能规划与 UI/交互偏好记录总账。
> 本项目的分析师在制定任何施工方案前，必须强制读取并严格对齐本文档中的所有规则与偏好，绝不允许另起炉灶、重复造轮子或编写与之冲突的逻辑。

---

## 0. 顶层架构原则

### 0.1 职责单一（Single Responsibility Principle）
凡是违反职责单一、逻辑不纯、跨模块相互耦合抢锁的实现，一律视为失败。在 UI 交互与大批量数据处理时，必须严格解耦，视图类不应包含复杂的持久化大事务、磁盘 I/O 或大文件扫描逻辑，必须提取专门的业务处理器（Processor）与数据工厂（Factory）。

### 0.2 双轨路由物理隔离
应用分为 **"SQLite 内存模式"（Library模式 / 镜像加速态）** 和 **"磁盘目录模式"（DiskNav模式 / 实时 I/O 驱动）** 2 种：
* 两者运行时各自独立，相互不干扰、井水不犯河水。
* 不共享判断逻辑、不共享数据加载路径。
* 磁盘模式下进行写操作（设色、加星、打标、加备注等）产生的任何元数据，**100% 绝对禁止写入/溢流到 SQLite 本地数据库中**。必须独占调用离散元数据缓存类 `AmMetaJson` 读写至对应的盘符离散 `.json`（例如 `ArcMeta.cache/路径Hash.json`）中。

### 0.3 核心事件方案命名法与历史只读铁证
- **命名规范**：方案文件彻底废除 `Modification_Plan-N.md` 数字命名，改用可读性极强的 `核心事件名.md` 命名。
- **只读升级机制**：已有方案文件为只读历史铁证，严禁做任何直接原文件修改。升级迭代版本需采用 `核心事件名-1.md`、`核心事件名-2.md` 的递增方式新建，完美保留每一次技术方案演进全过程。

## 1. 核心功能与绑定规则

### 1.1 “我的分类”与“快速访问”的联动机制
* **共享数据模型**：两者本质上共享同一套底层物理分类表 `categories`。
* **置顶状态关联**：每个分类节点有 `pinned`（布尔）属性。
  - 自定义分类树（我的分类）：挂载全部自定义类别。
  - 置顶列表（快速访问）：系统遍历分类，仅当其 `pinned` 属性为 `true` 时，在此分组下为其建立一个 **镜像代理节点（Mirror Item）**。
  - 镜像代理节点与原分类物理节点绑定相同的 `IdRole`、`TypeRole` 等属性，实现高强度的完全联动。点击两边任意一处的同一 ID 节点，最终都会穿透并分发给底层同一个业务 ID。
* **右键菜单交互联动**：
  - 未置顶时，物理右键显示“添加至‘快速访问’”，点击后将 `cat.pinned` 改为 `true`，通过 `CategoryRepo::update(cat)` 持久化落盘并刷新模型。
  - 已置顶时，物理右键显示“从‘快速访问’中移除”，点击后将 `cat.pinned` 改为 `false`，通过 `CategoryRepo::update(cat)` 持久化落盘并刷新模型。

### 1.2 分类文件加载与架构收拢规范
* **数据库绝对主导原则**：在侧边栏分类模式下加载分类内容（无论是列表展现、条数统计、对账等），**100% 仅允许通过中心化的 SQLite 数据库关联表（`category_items`）直接读取映射数据**（如调用 `CategoryRepo::getItemsInCategory` / `getItemsRecursive`）。
* **物理路径前缀枚举的废除**：严禁采用针对根分类（`parentId == 0`）物理路径进行前缀模糊匹配内存扫描（`MetadataManager::forEachCachedItem`）的方法来枚举和计数分类文件。
* **辅助元数据过滤规范**：磁盘上物理存在的 `.scch` / `metadata.scch` 后缀名文件是系统的辅助元数据缓存。在分类和文件列表检索时，必须统一且始终将其过滤掉，防止辅助文件冒充正常资产加载。修改注释或清理代码时，不得改动过滤逻辑本身，仅可将其中的描述性英文（如 SCCH 架构）修正为中性含义描述。

### 1.3 调试性日志与生产分级保留规范
* **纯调试性日志物理删除**：开发阶段用于进度提示、临时变量值、"进入XX函数""正在执行XX步骤"等对用户/运维无排障价值 of 输出（`qDebug`、`qInfo`、`std::cout`、`printf` 且内容无失败/异常语义的），必须物理删除，绝不采用注释行或宏包裹保留。
* **生产级异常分级保留**：内容属于失败、严重的磁盘 I/O 异常、SQLite 语句编译 prepare 失败等具有生产排障和运维价值的情况，哪怕历史被标记为 `qDebug` / `qInfo`，也必须保留并升格为 `qWarning` 或 `qCritical` 等级，不允许删除。

### 1.4 万级拖拽归类性能
- **发起阻断消除**：拖拽发起时（`startDrag`），严禁使用 `QFileInfo::exists` 等任何涉及同步磁盘 I/O 阻塞 of 判定，因为界面上可见的项路径必定存在。
- **悬停 O(1) 过滤**：拖拽悬停时（`dragEnterEvent`/`dragMoveEvent`），严禁对万级路径执行全文本序列化与 `hasUrls()` 解析。必须使用 O(1) 复杂度的 MIME 字符串检测 `hasFormat("text/uri-list")` 瞬间拦截或允许。
- **后台异步大事务**：当有大量路径（最高可达数万）被拖拽放入分类时，严禁在主线程直接循环执行 SQL 或逐个关联。必须将路径提取、受控状态判定、归属转换、以及数据库写入等全部繁重逻辑交由后台线程（如 `QtConcurrent::run`），并统一使用 `SqlTransaction` 开启批量显式大事务。
- **SRP 架构与三大件协同规范**：
  - `CategoryDropProcessor` 作为拖拽后台业务处理器，专门负责路径后台验证、跨盘迁移决策、进度计算推送（`progressUpdated` 信号）及数据库大事务关联。
  - `TaskProgressToolBar` 作为无感底栏进度工具栏，负责实时响应进度更新并展现剩余预估秒数，支持用户一键取消。
  - `DuplicateConflictDialog` 与查重服务（`DuplicateDetectorService`）作为处理完成后的追溯决策链，自动检测新导入的重复文件并提供“使用已存在”或“保留两者”的用户控制选项。
  - `DragPayloadFactory` 作为拖拽数据工厂，专门负责快速无阻塞打包/判定 MIME 数据及解析提取物理路径，使 View 层回归“单纯视图绘制和事件响应”的职责。

### 1.5 批量创建功能
- **规则解耦**：批量创建功能（`BatchCreateDialog`）支持与批量重命名一致的组件规则架构。用户可以通过交互来增删和配置以下 4 种规则，以作为创建路径模板：
  - 固定文本（Text）
  - 序列数字（Sequence）
  - 原文件名（OriginalName，当提供了当前选中文件作为参数时有效）
  - 日期格式（Date）
- **高阶处理管道**：对话框提供一个数量控制组件，让用户指定本次需要批量创建的项数 $K$，并通过一个文本输入框让用户直接配置规则，最后循环 $0$至 $K-1$ 依次格式化计算出每一项的目标新名称并物理创建。

### 1.6 操作状态快照与 UndoToastOverlay 通用撤销机制
- **状态快照抽象 (Operation Snapshot Engine)**：
  - 在执行关键数据修改操作（包含：重命名、批量重命名、拖拽分类、删除/移入回收站、添加至收藏、归类到...）之前，系统必须统一通过 `OperationSnapshotManager`（或对应快照引擎）捕获操作前受影响资产的完整元数据快照（如原始路径、分类 ID 映射、收藏/星级状态、标签等）。
  - 快照对象支持单一与批量操作的开箱即用打包，避免各 UI 动作自行编写零散的状态记录逻辑。
- **与 UI 撤销浮窗 (UndoToastOverlay) 的无缝桥接**：
  - 任何包含状态修改的操作执行成功后，一律通过 `UndoToastOverlay::instance()->showToast()` 弹出 Snackbar 提示。
  - 传入的 `undoCallback` 必须直接绑定快照引擎生成的 `restore()` 闭包或对应 UndoCommand，实现一键、原子化、原路状态回滚。
- **内存与作用域安全**：
  - 撤销回调函数与其内部持有的快照数据必须采用值拷贝或弱引用句柄（`std::shared_ptr` / `QPointer`），防止由于被操作 UI 控件被销毁导致撤销回调触发野指针崩溃。

### 1.7 磁盘模式元数据双向加载与 MetaPanel 编辑态隔离规范
- **磁盘模式 `.ArcMeta.json` 双向对称加载 (Disk Mode Dual-Way Persistence)**：
  - 磁盘目录模式（DiskNav）下对元数据的读写必须形成完全对等的闭环。
  - 写入时：通过 `AmMetaJson` 将相对文件名 `fileName` 的属性更新至所在目录隐藏的 `.ArcMeta.json` 文件中。
  - 读取时：在 `DiskScanService` 或 `MetadataManager` 扫描/载入磁盘目录的第一时间，必须显式调用 `AmMetaJson::load()`，将相对文件名解析恢复为规范化的绝对物理路径（`absolutePath`），并注入到内存快照 `m_snapshot` 中，确保 UI 与检索能 100% 读取到磁盘离散元数据。
- **MetaPanel 编辑态隔离与文本冲刷防护 (Edit State Isolation)**：
  - 在 `MetaPanel` 编辑器中输入文本（如备注、链接、标签等）时，必须设置严格的编辑状态锁（`m_isEditing`）。
  - 当某个编辑框拥有键盘焦点或正在被用户输入时，系统绝对禁止接受任何来自 `selectionChanged` 或后台异步刷新的全路径/默认文本冲刷覆盖。
  - `MainWindow` 在分发 `updateInfo` 时，必须严格区分文件名与全路径，绝对禁止将 `path` 误传给 `name` 属性导致文本框内容错乱。

### 1.8 拖拽导入查重与重复添加决策规范
- **重复添加对比对话框 (DuplicateConflictDialog)**：
  - 标题栏格式必须为 `重复添加提示 (N)`，其中 N 标识本次识别到的冲突组总数。
  - 对话框呈现双卡片（“已存在”与“新的文件”）对比视图，展示文件缩略图、文件名、尺寸/分辨率、文件大小及关联文件夹。
- **“全部应用 (N)”批量决策机制**：
  - 底部操作栏必须提供 `QCheckBox` 控件 `[  ] 全部应用 (N)`，动态绑定冲突总数 N。
  - 当用户选中“使用已存在文件导入”或“保留两者”并勾选 `全部应用 (N)` 提交时，系统直接将该处理策略批量应用至后续全部 N-1 组冲突项，不再逐个弹窗中断用户，实现零阻碍快速入库。

### 1.9 极速递进判重与文件哈希持久化
- **三级递进判重原理**：在执行重复检测时，采用“体积 $O(1)$” -> “快速采样 Hash” -> “全量 SHA256” 的递进判重流程。
- **快速采样 Hash 算法定义**：提取文件头部 $4\text{KB}$ 与尾部 $4\text{KB}$，文件小于 $8\text{KB}$ 时采用全量计算，耗时控制在 $1\text{ms}$ 以内。
- **全量 SHA256 缓存与落盘持久化**：首次遇到已有文件哈希缺失时，计算全量哈希并立即通过 `setSha256` 落盘持久化。在下一次判重中，直接在内存快照中以 $O(1)$ 复杂度直接进行全量哈希比对，实现万级导入的假死根除。

### 1.10 UI 物理排序稳定保底
- **置顶与文件夹排序恒常置顶规则**：文件夹、置顶项在升序与降序下永远恒常置顶，绝不因为 Descending 反转而下沉。置顶逻辑完全剔除 `sortOrder` 判定。
- **平局决胜排序 (Tie-breaker)**：当两个资产在对应排序维度（扩展名、大小、尺寸面积、评分等）的值相等时，100% 追加以 `localeAwareCompare` 对比 `filename`（文件名）作为平局保底决胜。
- **尺寸面积平局保底**：尺寸面积不仅对比 $W \times H$，平局时必须采用文件名保底排序，且当无宽高信息（如非图片、文档等 $W=H=0$）时，同样在 $0$ 面积的基础上按文件名平局决胜，杜绝界面列表无谓的随机抖动。

### 1.11 列表视图列标题中文名称绑定规范
- **列表模型标题绑定规则**：列表视图绑定的数据模型（如 `LibraryAssetModel` 和 `DiskItemModel`）必须显式重写 `headerData` 方法。
- **列对应中文字符串定义**：在 `orientation == Qt::Horizontal` 且 `role == Qt::DisplayRole` 的情况下，必须严格根据列的 section 返回对应中文字符串：
  - `0` -> `"名称"`
  - `1` -> `"状态"`
  - `2` -> `"评分"`
  - `3` -> `"尺寸"`
  - `4` -> `"类型"`
  - `5` -> `"大小"`
  - `6` -> `"修改日期"`
- 严禁依赖默认实现或返回数字作为列标题，保障工业级界面的中文化完整度。

### 1.12 “添加日期”排序选项数据源与稳定排序规范
- **选项显示动态隔离规则**：“添加日期”这一排序选项**仅允许在内存模式下显示**。在构建右键菜单（如 `ContentPanel::onCustomContextMenuRequested`）时，必须通过 `isMirrorSource()` 校验。若为磁盘导航模式（`isMirrorSource() == false`），必须屏蔽“添加日期”选项。
- **降级保护生效规则**：在底层代理排序引擎 `FilterProxyModel::lessThan` 比较时，若当前排序类型为 `SortByAddedDate` 且非内存模式，必须将比较类型物理强制退化为 `SortByName`（名称排序），确保该排序方式**仅在内存模式下起作用**。
- **分组排序严格弱序（Strict Weak Ordering）契约**：在对包含分组信息的记录（如回收站垃圾箱分组）进行比较时，必须使用严密的单向优先级定义（非分组 -> `0`，Library -> `1`，DiskNav -> `2`），严禁使用产生双向 `true` 的逻辑比较，彻底抹除 C++ 排序崩溃隐患。

## 2. UI 视口板块划分与数据联动规范

为了保证整个应用视口在超大型多维检索和高性能单击状态下的极致稳定，全应用的主视口在初始化及布局（`MainWindow`）时必须严格对齐并划分为以下 **5 大核心主业务面板板块**，并辅以一个**特殊的专项独立视图（模式）**。分析师后续建立任何联动信号或新面板挂载时，严禁打破此板块边界或胡乱跨域侵入：

### 2.1 五大核心板块分工与分类面板构成

#### 2.1.1 分类面板 (CategoryPanel) — [ 占位比例: 230 ]
* **职责**：逻辑分类树渲染器。管理“我的分类”及“快速访问”列表，负责分类增删、锁定状态交互。
* **分类树节点物理层次（严格物理顺序，自上而下挂载）**：
  1. **系统逻辑桶（System Logic Buckets）**：
     - **全部数据**：`sysId = -1`，类型标识 `all`。展示并检索非回收站非文件夹的资源库全量资产。
     - **未分类**：`sysId = -2`，类型标识 `uncategorized`。筛选排除在任何自定义分类之外的非回收站文件。（具体见 2.1.1.1）
     - **未标签**：`sysId = -3`，类型标识 `untagged`。筛选无自定义标签（`tags` 为空）的非回收站文件。
     - **最近访问**：`sysId = -6`，类型标识 `recently_visited`. 筛选 24 小时内有访问活动的非回收站文件。
     - **标签管理**：`sysId = -7`，类型标识 `tags`。单击后物理切断主视口，专项切换至全局标签管理大屏。
     - **回收站**：`sysId = -8`，类型标识 `trash`。专职展现和一键清空/恢复被标为 `is_trash = 1` 的库内被删资产，不接受任何形式的外部拖入或粘贴。
  2. **物理托管库根分类（Managed Library Roots）**：
     - **挂载标准**：自动探测盘符，自愈生成 `parentId == 0` 且名称匹配 `ArcMeta.Library_` 前缀（如 `ArcMeta.Library_G`）的根分类项。
     - **层级归属**：独立在最外层（不作为“分类”子项挂载），其文件数目通过所属数据库 `category_items` 完全核算。
     - **核心设计定义（筛选入口，而非分类语义本身）**：
       托管库根分类在侧边栏中仅作为 **筛选入口（Filter Scope）** 存在，其**不构成系统真正的“已分类整理”这一业务概念**。
       - 资产挂载在托管库根分类下，仅仅代表其物理归属，与该资产“是否已被用户手动归纳整理、分类”是完全独立的两个物理维度。
       - **统计计数与过滤绝对原则**：
         在计算 **“未分类”（uncategorized）** 的资产统计和对账时，必须使用类似 `NOT IN (SELECT id FROM categories WHERE parent_id=0 AND name LIKE 'ArcMeta.Library_%')` 的排他断言进行过滤拦截。
         **绝对不许在任何地方将物理库根分类当作“已分类”标志，从而导致统计漏记或归零！**
  3. **“快速访问”分组节点（zap_filled 星标，#F1C40F 黄色）**：
     - **挂载机制**：由系统在运行时，将所有 `cat.pinned == true`（置顶）的自定义分类以 **镜像代理节点（Mirror Item）** 挂载于该大标题节点之下，不随大标题一起折叠。
  4. **“分类”主标题组节点（category 蓝标，#378ADD 蓝色）**：
     - **挂载机制**：层级折叠组。代表用户完全自定义的分类树入口。
     - **子项结构**：树状挂载所有 `parentId > 0` 的自定义分类。
* **信号联动**：向主导航中枢（`unifiedNavigateTo`）分发分类 ID。

#### 2.1.1.1 “未分类（Uncategorized）”的业务定义与自愈规则

“未分类”作为系统核心逻辑桶，具有极其清澈和排他的业务定义。开发、维护和统计时，必须100%强制遵循以下规则：

* **核心定义**：
  **未分类 = 该资产在 `category_items` 表中，不存在任何指向“用户手动创建的分类”或“自动创建的分类”（即 `category_id > 0`，且排除挂载在托管库根分类——即 `parent_id == 0` 且名称形如 `'ArcMeta.Library_%'` 的纯物理记账归属）的关联记录。**
  
* **回收站流程强制物理行为**：
  1. 资产进入回收站（`moveToTrashBatch`）的第一时序，系统必须物理删除该资产在 `category_items` 表里的**所有分类关联记录**（无论是自定义分类、子树分类、还是自动挂载的托管库根分类关联），然后插入 `category_id = TRASH_CATEGORY_ID` 的记录。
  2. 资产从回收站恢复时（`restoreFromTrashBatch`），**原有的分类关联一律不再保留，原路归零**。系统直接显式地往 `category_items` 表里写入一条指向 `UNCATEGORIZED_CAT_ID` (-2) 的新纪录，归入“未分类”桶。
  
* **防偏离防失真自愈规范**：
  当资产从回收站恢复（写入 `UNCATEGORIZED_CAT_ID` 新纪录）时，系统必须显式且精确地对 `s_uncategorizedCount` 进行更新（例如对恢复的资产增量执行 `s_uncategorizedCount.fetch_add(delta)`），防止因操作遗漏导致侧边栏原子计数器静默偏离真实对账值！

## 3. UI/交互与偏好规范（阻止重复造轮子）

### 3.1 输入框一键清除按钮（Clear Button）
* **唯一标准**：一律使用 Qt 原生的 `setClearButtonEnabled(true)`。
* **红线**：严禁通过 `addAction`、手动重写 Paint 绘图事件或自定义 QPushButton 去模拟一键清除逻辑。

### 3.2 窗口置顶（Window Stays on Top）
* **唯一标准**：一律使用 Win32 原生的 API 函数 `SetWindowPos`（传入 `HWND_TOPMOST` 或 `HWND_NOTOPMOST`），并配合 `SWP_NOSENDCHANGING` 标志位实现。
* **红线**：严禁使用 Qt 的 `setWindowFlag(Qt::WindowStaysOnTopHint)` 或任何导致窗口发生销毁重建、句柄变动的操作。

### 3.3 标题栏按钮（Hover & Pressed 样式）
* **唯一标准**：
  - Hover（悬停）背景色：`#3E3E42`（系统预设：`Style::HoverBackground`）
  - Pressed（按下）背景色：`#4E4E52`（系统预设：`Style::PressedBackground`）
* **红线**：严禁在样式表或绘图事件中手写使用半透明 `rgba` 颜色蒙版。

### 3.4 其他 UI 对齐偏好
* 所有新 UI 组件、新样式在实现前，**必须强制在代码库中进行同类案例“考古”（Code Archaeology First）**。如果已经存在同类组件（如卡片圆角、颜色条、进度条），必须以该现有案例为模板保持 100% 样式、间距、调色和交互一致，严禁新建一套样式定义。

# 扫描数据中进度条及 ETA 预计耗时同步方案 —— Modification_Plan-107.md

> 状态：已批准，执行中

## 1. 任务背景
在文件监控与数据扫描系统中，数据扫描进度、文案和耗时估算的精确度直接影响用户的感知体验。

原来的设计中文案使用“正在同步元数据...”，且计算百分比时使用了简单的经验预估，其进度条在多任务并发时可能出现比例回退。

本方案旨在对极光进度条进行精细重写：
1. 修正文案为“扫描数据中...”。
2. 耗时机制更正为根据进度推算“预计耗时” (ETA)。
3. 在开始时锁定总量并基于完成比例计算，确保进度条严格从左往右单向递增推进，消除回退。

## 2. 问题定位
1. **经验估算导致比例跳跃**：以前采用 `qBound(10, 100 - (pendingCount * 2), 95)`，当由于异步扫描导致 `pendingCount` 时大时小时，百分比会发生抖动或减少，进度条发生视觉回退。
2. **文案和预计耗时缺失**：常态的耗时显示是已用时间，而用户在长时间扫描时更期待知道大概还需多久完成 (ETA)。

## 4. 详细解决方案

### 4.1 引入 `m_totalBatchCount` 锁定总量
在 `MainWindow` 类中引入私有变量 `m_totalBatchCount`，初始值为 `0`。当检测到扫描/同步任务启动时，将其设置为当前的 `pendingCount` 并锁定。若之后由于追加产生了更大的 `pendingCount`，则动态扩张 `m_totalBatchCount`，使其作为总量母数。

### 4.2 高精度的预计剩余耗时 (ETA) 估算
在 timeout 回调中，当进度百分比 `currentPct >= 5` 时，利用比例推导估算剩余完成时间：
```cpp
double estRemainingSec = elapsedSec * (100.0 - currentPct) / (double)currentPct;
```
将其转换为 `X.Xs` 形式（保留1位小数），从而对状态栏耗时文案做精确的更新。

### 4.3 递增进度条控制
按公式 `completedCount = m_totalBatchCount - pendingCount` 严格计算当前完成比重。限制数值在 `[1, 99]` 之间（完成时直接拉满 `100`），保证其严格单向推进、绝不发生任何比例回退跳跃。

## 6. 实现准则与预警【核心】
1. **防止除零异常**：在计算 ETA 动态推导时，必须保护分母（`currentPct` 必须大于等于 5 且不能为 0），否则降级输出“计算中...”，防止引起程序崩溃。
2. **总量防溢出**：在不断追加任务时，若 pendingCount 超出 `m_totalBatchCount`，必须更新 `m_totalBatchCount`。
